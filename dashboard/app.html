History before today is synthetic demo data. Meals closed in this app are added as real history.

Everyone is present by default. A student only has to act if they will not eat. Absences are stored per meal in the absences table (one row per student and meal, enforced by a UNIQUE constraint) and feed the agent's forecast. Once a meal's plan is approved its attendance is locked.

A planning agent: it predicts how many students will really eat (opt-outs plus the usual no-show rate from past service), proposes how much to cook, checks stock, and waits for a human to approve. It is a statistical model (exponential smoothing + safety margin), not a language model, and it runs fully offline. After service you close the meal with the real count and the agent learns from it.

How good is it? · replay of the last 7 days

Each past meal is forecast using only data from before that day. The "old habit" is cooking for everyone who did not opt out. Past data is synthetic demo data, so treat the percentages as a demonstration of the method.

Five agents, each in its own thread with its own inbox queue (the same producer-consumer pattern as the C++ event queue), talking only by messages. Every message is saved in the agent_messages table. Nothing is applied automatically: you approve each meal.

Uses today's open meals, current absences and stock.

Starts two separate programs joined by a pipe: event generator → pipe → IPC server (queue, 3 worker threads, SQLite). This page only reads the database they write.
